## 1. Executive Summary

The **Admin Panel** is the site owner's private command center for MyLib. It provides:

- **Platform Health Monitoring** — real-time stats on users, books, reviews, and activity.
- **User Management** — search, view, ban, promote, and control user accounts.
- **Content Moderation** — review reports, delete inappropriate content, ban bad actors.
- **Custom Messaging** — push notifications to any user or all users, with severity colors.
- **Platform Configuration** — Push notification providers, email providers, AdSense, AI, feature flags.
- **Monetization Control** — define Free/Pro plans, pricing, features, and discounts.
- **Data Management** — backups, exports, and destructive actions.

The Admin Panel is **invisible to non-admins** — hidden from navigation, protected at the route level, and secured by Firestore rules.

## 3. Technical Architecture

- **Admin tab persistence:** Use Zustand to persist the active tab across sessions; validate the stored tab and fall back to Dashboard.

- **Routing:** `/admin/*` wrapped in `<AdminRoute>` which redirects non-admins to `/library`.
- **Layout:** Reuses the existing `AppLayout` with an added "Admin" sidebar entry (Lucide `Shield`, not `ShieldCheck`) — only visible to admins. Keep the mobile bottom navigation at four slots: replace Insights with Admin for admins only; non-admins retain Insights. Mobile admins can reach Insights through the profile menu.
- **Tabs:** 6 tabs across the top: Dashboard, Users, Moderation, Messaging, Plans, Settings.
- **State:** TanStack Query for server state, Zustand for local UI state.
- **Design:** Matches the rest of MyLib — solid backgrounds (no `.glass`), Light/Dark/Sepia themes, Fraunces + Raleway fonts.
- **Data Model:** New Firestore collections: `adminConfig` (documents `main` and `public`), `adminAuditLog`, `platformPlans`, `platformDiscounts`, `systemNotifications`.

## 4. Notification System Architecture 🆕

### 4.1 Provider Abstraction Layer

The notification system uses a **Provider Abstraction Layer** to support multiple push notification backends. This means you can switch providers at any time from the Admin Panel without touching code.

**Supported Providers:**

| Provider | Type | Default | Cost |
|---|---|---|---|
| **Firebase Cloud Messaging (FCM)** | Managed | ✅ Default | Free |
| **Self-Hosted Web Push** | Self-hosted (VAPID) | Optional | Free |
| **OneSignal** | Managed | Optional (future) | Free tier available |

**How It Works:**

1.  **Standard Interface:** All providers implement a common `PushProvider` interface:
    ```typescript
    interface PushProvider {
      subscribe(userId: string, subscription: PushSubscriptionJSON): Promise<void>;
      unsubscribe(userId: string): Promise<void>;
      send(targetUserIds: string[] | 'all', payload: PushPayload): Promise<SendResult>;
      test(): Promise<{ ok: boolean; message: string }>;
    }
    ```
2.  **Adapter Pattern:** Each provider is wrapped in an adapter class (e.g., `FCMAdapter`, `WebPushAdapter`).
3.  **Runtime Selection:** The active provider is read from `adminConfig/main.integrations.push.provider`. Switching providers only requires changing this value and re-registering existing subscriptions (if the browser subscription format differs).
4.  **Subscription Storage:** Each user's push subscription is stored in `users/{uid}/private/data.pushSubscriptions`, keyed by provider name:
    ```typescript
    {
      pushSubscriptions: {
        fcm: { token: string, platform: 'web', registeredAt: Timestamp },
        webpush: { endpoint: string, keys: { p256dh, auth }, registeredAt: Timestamp }
      }
    }
    ```

### 4.2 Default: Firebase Cloud Messaging (FCM)

**Configuration (in Admin Panel → Settings → Integrations → Push Notifications):**
- **Provider Dropdown:** FCM (default) / Self-Hosted Web Push / (future: OneSignal).
- **FCM VAPID Key:** Text input (from Firebase Console → Cloud Messaging → Web Push certificates).
- **Enable FCM:** Toggle.
- **Service Worker URL:** Auto-configured (`/firebase-messaging-sw.js`).
- **Test Push Button:** Sends a test notification to the admin's own browser.

**Client Integration:**
1.  On first load, `firebase-messaging` requests notification permission.
2.  If granted, generates an FCM token and saves it to `users/{uid}/private/data.pushSubscriptions.fcm`.
3.  The service worker receives push events and displays notifications.
4.  Clicking a notification navigates to the appropriate `actionLink`.

**Backend:** Sending uses the FCM HTTP v1 API through the trusted cPanel Node.js backend for v1 (subject to hosting support), using Firebase Admin SDK and server-side credentials. The browser must never send with a server key. Cloud Functions on Blaze are an optional alternative; Firebase Spark does not support deploying Cloud Functions.

### 4.3 Optional: Self-Hosted Web Push

**Configuration:**
- **VAPID Public Key:** Auto-generated once, displayed for the client to use.
- **VAPID Private Key:** Password input (never displayed after save).
- **VAPID Subject:** `mailto:admin@softrly.com` (or similar).
- **Endpoint URL:** The URL of your self-hosted push server (e.g., `https://push.softrly.com`).
- **Enable Self-Hosted:** Toggle.

**Backend:**
- A small Node.js server (can run on cPanel via Node.js Selector, or on a small VPS) using the `web-push` npm package.
- Listens for admin API calls from the frontend, fetches subscriptions from Firestore, and dispatches pushes.
- Requires HTTPS (mandatory for Web Push). Your cPanel host already provides this via AutoSSL.

### 4.4 Sending Custom Notifications (Messaging Tab)

The **Messaging Tab** in the Admin Panel allows sending custom notifications to any user or all users:

**Compose Form:**
- **Target:** All Users / Pro Users / Free Users / Specific User.
- **Severity:** Info (blue) / Success (green) / Warning (amber) / Danger (red).
- **Title:** Max 100 chars.
- **Body:** Max 500 chars.
- **Action Link (Optional):** URL or route.
- **Action Label (Optional):** Button text.
- **Send Now / Schedule:** Date-time picker.
- **Live Preview:** Renders the notification as it will appear.

**Delivery Logic:**
1.  Admin submits the form → writes to `systemNotifications` collection.
2.  The trusted backend worker reads the target filter and fetches matching `pushSubscriptions` from Firestore.
3.  The active push provider sends to all matching subscriptions.
4. The notification is also written to each user's `users/{uid}/notifications` subcollection (so they see it in the bell dropdown even if they missed the push). The backend records `deliveryCount` as successfully created inbox records; it is not a read/open count.

**Scheduling:** A cPanel cron job runs every five minutes and calls the authenticated cron-only `POST /admin/process-scheduled` endpoint. It selects due unsent records, claims them transactionally, fans them out idempotently, and records `sent`, `failed`, or retryable processing state. The implementation and runtime contract are defined in the companion Architecture document.

## 5. Email System Architecture 🆕

### 5.1 Provider Abstraction Layer

Like push, the email system uses a **Provider Abstraction Layer**:

**Supported Providers:**

| Provider | Type | Default | Free Tier |
|---|---|---|---|
| **Resend** | Managed | ✅ Default | 3,000/month (100/day) |
| **Brevo** (Sendinblue) | Managed | Optional | 300/day |
| **Mailtrap** | Managed | Optional | 4,000/month |
| **SendGrid** | Managed | Optional | 100/day (first 60 days) |
| **SMTP (Custom)** | Self-hosted | Optional | Depends on host |
| **Custom SMTP via cPanel** | Self-hosted | Optional | Free (uses your cPanel mail) |

**Standard Interface:**
```typescript
interface EmailOptions {
  to: string | string[];
  subject: string;
  html: string;
  from?: string;
  replyTo?: string;
  variables?: Record<string, string>;
}
interface EmailResult { id: string; ok: boolean; error?: string; }
interface EmailProvider {
  sendEmail(options: EmailOptions): Promise<EmailResult>;
  sendBatch(recipients: string[], subject: string, html: string): Promise<EmailResult[]>;
  test(): Promise<{ ok: boolean; message: string }>;
}
```

### 5.2 Default: Resend

**Why Resend?**
- Modern, developer-friendly API.
- Excellent React Email template support.
- 3,000 emails/month free.
- Simple API key authentication.

**Configuration (in Admin Panel → Settings → Integrations → Email):**
- **Provider Dropdown:** Resend (default) / Brevo / Mailtrap / SendGrid / Custom SMTP.
- **Resend API Key:** Password input (from resend.com dashboard).
- **From Email:** `noreply@softrly.com`.
- **From Name:** `MyLib Team`.
- **Reply-To:** `support@softrly.com`.
- **Enable Email:** Toggle.
- **Test Email Button:** Sends a test to the admin's email.

### 5.3 Alternative: Custom SMTP via cPanel

If you want to avoid third-party email providers entirely, you can use your cPanel's built-in mail server:

- **SMTP Host:** `mail.softrly.com`.
- **SMTP Port:** 587 (TLS).
- **SMTP User:** `noreply@softrly.com`.
- **SMTP Password:** Password input.
- **Enable TLS:** Toggle.

**Limitations:**
- Deliverability is lower than managed providers (emails may land in spam).
- Free but requires managing sender reputation.
- Best for low-volume, non-critical emails.

**Recommendation:** Start with **Resend** for reliability. Switch to Custom SMTP only if you need complete independence and can tolerate deliverability issues.

### 5.4 Email Templates

**Templates managed by the admin:**
- **Welcome Email** (on signup).
- **Password Reset** (delegated to Firebase Auth by default).
- **Weekly Digest** (future).
- **Custom Email** (one-off sends to a user or all users).

**Template Editor:**
- Subject line input.
- Rich-text or Markdown body editor.
- Variable placeholders: `{{username}}`, `{{displayName}}`, `{{booksCount}}`.
- **Variable substitution:** Use `{{variableName}}` syntax. The `variables` object replaces matching placeholders in both `subject` and `html` before sending. Missing variables are replaced with an empty string and logged server-side; do not log secrets or full sensitive message content.
- Live preview.
- Send test button.

**Configuration security:** `adminConfig/main` is admin-readable and contains operational configuration; `adminConfig/public` is publicly readable and contains only landing-page content intended for public display. API keys, SMTP passwords, VAPID private keys, service credentials, and other secrets MUST live in server-only environment/secret storage, not in Firestore documents readable by browser clients (including admins). The settings UI may display masked status and submit secret changes to the authenticated backend.

## 7.1 First Admin Bootstrap and Initial Data

**First admin:** Bootstrap the owner's verified Firebase UID out-of-band through Firebase Console (`users/{uid}.role = 'admin'`) or a one-time trusted script using Firebase Admin SDK. Do not use `VITE_ADMIN_EMAIL` or client-side `AuthContext` code to grant admin: Vite variables are public, and Firestore rules must not permit self-promotion. Remove/disable any one-time script after use.

**Initial defaults:** On first authorized admin visit, an idempotent `seedDefaults` routine ensures `adminConfig/main`, `adminConfig/public`, `platformPlans/free`, and `platformPlans/pro` exist. It must create only missing documents, never overwrite existing settings, and handle concurrent visits safely (transaction/create-if-absent). Prefer server-side seeding where practical. Include default field values in implementation constants and test repeat/concurrent execution.

## 8. Firestore Rules (Admin Additions)

```javascript
function isAdmin() {
  return isSignedIn()
    && exists(/databases/$(database)/documents/users/$(request.auth.uid))
    && get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'admin';
}

match /adminConfig/main {
  allow read, write: if isAdmin();
}

match /adminConfig/public {
  allow read: if true;           // Public landing-page content only
  allow write: if isAdmin();
}

match /platformPlans/{planId} {
  allow read: if true;          // Public read for landing page pricing display
  allow write: if isAdmin();
}

match /platformDiscounts/{discountId} {
  allow read: if true;
  allow write: if isAdmin();
}

match /systemNotifications/{notificationId} {
  allow read, write: if isAdmin();
}

match /adminAuditLog/{logId} {
  allow read, create: if isAdmin();
  allow update, delete: if false;   // immutable
}

// Users: only admins can change role/plan/banned
match /users/{userId} {
  allow update: if isSignedIn()
    && (
      (userId == request.auth.uid
        && resource.data.get('role', 'user') == request.resource.data.get('role', 'user')
        && resource.data.get('plan', 'free') == request.resource.data.get('plan', 'free')
        && resource.data.get('banned', false) == request.resource.data.get('banned', false))
      || isAdmin()
    );
}
```
