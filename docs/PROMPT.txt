# FIX#01: Mobile Add-Book "+" Button

Currently, in the mobile view, the floating **"+"** button directly opens the **Add Books Manually** form.

Change this behavior.

When the user taps the mobile "+" floating action button, show an appropriate selection UI with at least these options:

1. **Scan Barcode**
2. **Add Books Manually**

The user should be able to choose either workflow.

### Scan Barcode

* Reuse the application's existing barcode-scanning functionality if one already exists.
* If barcode scanning functionality already exists elsewhere in MyLib, reuse the same implementation rather than creating a second scanner.
* After scanning a valid barcode, continue through the existing book-add/import workflow.
* Handle invalid/unrecognized barcodes gracefully.
* Handle camera permission denial/errors gracefully.

### Add Books Manually

Selecting this option should open the existing manual book-add form exactly as it currently works.

Do not unnecessarily redesign the manual form.

### UI

The selection UI may be implemented as a bottom sheet, action sheet, dialog, or another pattern consistent with MyLib's existing mobile UI.

It should be simple and obvious.

### Important

* This change applies to the **mobile view**.
* Do NOT change the desktop "+" behavior unless the existing desktop implementation specifically requires it.
* Do not duplicate barcode-scanning logic if it already exists.

# FIX#02: Wishlist Books Should Not Appear in Main Library

Currently, when a user marks a book as **Wishlist**, the book still appears in the main Library tab.

Change this behavior.

### Required behavior

If a book's status/state is **Wishlist**:

* It must NOT appear in the main **Library** tab.
* It must appear only in:
  **My Books → Wishlist**

Books that are not Wishlist should continue behaving exactly as they currently do.

### Important

* Do not delete Wishlist books from the database.
* Do not remove them from the user's collection.
* This is a visibility/filtering change, not a deletion.
* Make sure search/filter/count logic does not accidentally reintroduce Wishlist books into the main Library tab.
* Verify that Wishlist books remain accessible from the Wishlist sub-tab.
* Preserve existing Wishlist functionality.

Also inspect whether the current Library query/filter is shared with other screens. Fix the root filtering logic rather than adding a fragile UI-only workaround.

# FEATURE#01: Bulk Book Actions

Allow users to select multiple books and perform actions on them at once.

The user should be able to enter a multi-selection mode and select multiple books.

Once books are selected, provide appropriate bulk actions for:

1. **Edit Status**
2. **Delete**
3. **Transfer**

The exact UI should follow MyLib's existing design language.

## Bulk Status

Allow the user to change the status of all selected books in one operation.

The operation should apply only to the selected books.

## Bulk Delete

Allow the user to delete all selected books.

Because this is a destructive action:

* Show a confirmation step.
* Clearly tell the user how many books will be deleted.
* Do not delete anything until the user confirms.

Example:

**Delete 8 books?**

This action cannot be undone.

## Bulk Transfer

Allow the user to transfer all selected books using the existing book-transfer functionality.

Reuse the existing transfer logic rather than implementing a second transfer system.

## Selection behavior

* Clearly indicate selected books.
* Show the number of selected books.
* Provide an obvious way to exit selection mode.
* Prevent accidental actions on unselected books.
* Handle zero selected books appropriately.
* Handle large selections efficiently.

Do not break normal single-book interactions.

# FEATURE#02: Library Report PDF

# FEATURE #02: Library Report PDF

Add a new feature to MyLib that allows the library owner/user to generate and download a **complete, professional Library Report as a PDF** from **Insights** tab(at the bottom).

**ADD OPTION FOR USER TO CHOOSE whether the pdf should include user's library only or also include the collaborators' library

This should NOT feel like a simple database export or plain book list. It should feel like a formal library statement/report — similar in presentation to a bank statement or annual institutional report.

## 1. Access

Add a **"Download Library Report"** option in Settings.

When clicked, generate the report using the library's current data and download it as a PDF.

The report must contain only data belonging to the currently authenticated user's library.

Do not expose data belonging to other users/libraries.

The design should be clean, professional, modern, and suitable for printing.

* 10 books
* 100 books
* 1,000+ books
* Potentially very large collections

Table headers should repeat when a table continues onto another page.

# 13. EMPTY / MISSING DATA

Handle missing data gracefully.

Examples:

* No books → display an appropriate empty-state message.
* No categories → do not generate a broken chart.
* No prices → do not display a misleading collection value.
* No lending data → omit or clearly mark the circulation section as unavailable.
* Missing author → display `—`
* Missing ISBN → display `—`
* Missing category → display `—`

Never display `undefined`, `null`, `NaN`, or broken placeholders in the final PDF.

---

# 14. DATA ACCURACY

All statistics must be calculated from the same current data shown by MyLib.

For example:

**Total Books** must correspond to the actual inventory.

**Total Collection Value** must be calculated from the actual recorded book values.

**Available Books + Issued Books** should be logically consistent with the application's book-status model.

Do not introduce a second or separate data source just for the PDF.

Reuse the application's existing data-access/business logic wherever possible.

If an existing function/service already calculates a statistic, reuse it rather than duplicating the calculation.

* Book data is scoped to the current library/user.
* Member/borrower information, if included, is also correctly scoped.
