# Audit only — I read all the Phase 6.3 files and made no changes. Findings below.

  1. PUSH

  - Valid systemNotifications write? Yes. useSendNotification commits one doc with target, targetUserId
  (null unless specific), severity, title, body, actionLink/actionLabel (null when blank), scheduledAt
  (Timestamp|null), sentAt (serverTimestamp|null), status ('scheduled'|'sent'), deliveryCount: 0, createdBy,
   createdAt. sanitizeFirestoreData correctly preserves the serverTimestamp() sentinel and Timestamp
  instances (non-plain prototypes pass through). It satisfies the admin-only systemNotifications rule.
  - Calls getPushProvider().send()? Yes — but only on the non-scheduled path, inside a try/catch, after the
  doc commit.
  - Does it POST to the backend? Yes, indirectly: adapter send() → postAdminEndpoint('/admin/send-push') →
  fetch('https://mylib-api.softrly.com/admin/send-push'). The call is made; the endpoint doesn't exist.
  - Payload shape per PushProvider? Yes. PushPayload = {title, body, severity, actionLink?, actionLabel?,
  icon?, metadata?}; the composer supplies exactly title/body/severity/(optional
  link/label)/metadata{target, targetUserId, notificationId}. icon is simply unused. (The first arg,
  targetUserIds, is wrong for pro/free — see BUGS.)
  - subscribe() implemented? No. FCMAdapter.subscribe and WebPushAdapter.subscribe are no-ops (void
  subscription; console.warn(...)). Worse, subscribe()/unsubscribe() are never called anywhere in src (grep:
   only the definitions).
  - Missing for FCM end-to-end (every step):
    1. Client init getMessaging(firebaseApp) — firebase/messaging is never imported; lib/firebase.ts
  initializes only app/auth/firestore.
    2. Notification.requestPermission() — absent.
    3. getToken(messaging, { vapidKey }) — absent.
    4. VAPID key wiring — adminConfig.integrations.push.fcm.vapidKey exists but is never read client-side.
    5. Token persistence — no users/{uid}/pushTokens/* collection, no write in subscribe(), no Firestore
  rule for it.
    6. A registration call site (on login/permission grant) — none exists.
    7. Service worker public/firebase-messaging-sw.js + registration — public/ has no SW.
    8. Backend POST /admin/send-push.
  1. Backend ID-token + admin-claim verification.
  2. Backend audience resolution (all/pro/free/specific → user IDs; pro/free are not even sent correctly).
  3. Backend token lookup + FCM HTTP v1 send (service account).
  4. Delivery write-back to systemNotifications.deliveryCount/status.
  5. Scheduler to process status === 'scheduled' docs.
  6. Inbox fan-out writing users/{uid}/notifications docs (Admin SDK required — client rule demands
  actorUserId == request.auth.uid).

  2. EMAIL

  - Calls getEmailProvider().sendEmail()? Yes.
  - Where does recipient come from? recipient = input.target === 'specific' && input.targetUserId ?
  input.targetUserId : input.target. So it's a UID for specific, or the literal target keyword
  ('all'/'pro'/'free') otherwise. AdminUserRecord has no email field, and users' emails live only in
  users/{uid}/private/data (owner-only rule). There is no uid→email resolution client-side — a real blocker
  for specific-user email.
  - Variable substitution? None client-side. EmailComposer builds variables only for specific (username,
  displayName); for all/pro/free it passes {}. Adapters forward options (including variables) to the
  backend. Despite EmailProvider.ts claiming it "Replaces {{variableName}}", neither the factory nor
  adapters do it. Net: passthrough; bulk sends carry no variable values at all, and the live preview renders
   raw {{displayName}}.
  - Batch path? Interface + both adapters implement sendBatch, but it is never called (grep shows
  definitions only). EmailComposer always calls single sendEmail with one to.

  3. SHARED

  - Token attach: Correct. adminBackend.postAdminEndpoint reads auth.currentUser, await
  currentUser.getIdToken(), sets Authorization: Bearer ${token}.
  - Errors without leaking token: Yes. Failures throw Admin backend request failed (${status}); the token is
   only ever in the header and never surfaces. (It also swallows the body and has no 401-specific handling.)
  - Audit for both? Yes, but inconsistently. Push: writeAuditLog(action:'send_notification') in the same
  batch as the doc. Email: commitAuditOnly(action:'send_email') after a successful send. Caveat: the push
  audit is written before the send and persists even when delivery fails.

  4. GAPS (what must exist for admin click → user inbox)

  - Endpoints: POST /admin/send-push, POST /admin/send-email, POST /admin/test-push, POST /admin/test-email
  (base https://mylib-api.softrly.com).
  - Backend must verify the Firebase ID token and the role == 'admin' claim.
  - Client push registration: getToken() + write users/{uid}/pushTokens/{token}; plus a Firestore rule for
  that subcollection; backend reads it.
  - FCM service worker (firebase-messaging-sw.js) + registration; VAPID key from adminConfig into getToken.
  - Audience → user resolution for all/pro/free/specific (client currently collapses pro/free to all).
  - Email address resolution: uid→email and all/pro/free→address list, server-side (private subcollection is
   owner-only).
  - Template substitution server-side for {{username}}/{{displayName}}/{{booksCount}}; bulk sends provide no
   variables from the client.
  - Inbox fan-out: create users/{uid}/notifications docs matching AppNotification (type, title, body, link,
  actorUserId, actorName, actorAvatar, read:false, createdAt, metadata) via Admin SDK.
  - Delivery bookkeeping: update systemNotifications.deliveryCount and set status:'failed' on failure.
  - Scheduler/consumer for status:'scheduled' documents.
  - Email history relies on post-filtering the 200 newest adminAuditLog rows — entries beyond that window
  are lost.

  5. BUGS

  - Audience downgrade: const target = input.target === 'specific' && input.targetUserId ? [uid] : 'all' —
  pro and free are sent to the provider as 'all', so segment targeting is lost on the direct-send path.
  - False "sent": the doc is committed with status:'sent' and sentAt before the push attempt; on failure
  it's never flipped to failed, and deliveryCount stays 0. History shows "sent" for undelivered pushes.
  - Scheduled pushes never run: status:'scheduled' is written but nothing consumes it.
  - Email to contract violation: a UID or the keyword 'all'/'pro'/'free' is placed in EmailOptions.to
  (declared as address/addresses).
  - Wrong audit count: email details.recipients is hardcoded 1 regardless of audience.
  - Bulk variables empty: non-specific emails send {} variables; placeholders are never replaced; preview
  shows literals.
  - No-op registration: subscribe()/unsubscribe() are stubs and uncalled → no tokens exist to deliver to.
  - enabled not enforced: getPushProvider/getEmailProvider construct and return a provider even when enabled
   === false; enabled gates only the cache, not the send.
  - test() masks errors: both adapters' test() catch everything and report "Backend not deployed yet" even
  for real failures (403/500).
  - Error masking in send: useSendNotification maps every thrown error to pushError:'Backend not deployed
  yet'.
  - Email history identity: targetLabel(toTarget(target), null) renders specific as "Specific user"
  (identity lost); sentAt is the audit createdAt, not an email send time.
  - No request timeout/abort in postAdminEndpoint — a dead backend can hang the mutation.

  6. VERDICT

  Not complete — and not "pending only the backend." The write path (systemNotifications doc, provider
  abstraction, token attachment, audit hooks) is architecturally sound and the doc is valid, but there are
  code gaps that also need fixing: push token registration is entirely absent (subscribe() is a no-op and
  never called, no getToken, no VAPID wiring, no service worker), pro/free audiences collapse to all, email
  has no address resolution and no variable substitution with an empty variable map for bulk, scheduled
  sends have no consumer, and success/failure state is recorded before the send and never corrected. The
  backend is necessary but not sufficient.
