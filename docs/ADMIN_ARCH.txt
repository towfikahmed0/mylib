## 1. Executive Overview

**Charting:** Reuse the project's existing `chart.js` + `react-chartjs-2` dependencies used by Insights. Do not install another chart library. **Admin tab state:** Use the existing Zustand UI-state approach to persist the active admin tab across sessions (with a safe default and validation of stored tab values).

The Admin Panel is built as a **modular, provider-agnostic system** with clear separation between:

- **Presentation Layer** — React components (tabs, cards, tables)
- **Data Layer** — TanStack Query hooks + Firestore
- **Provider Layer** — Abstraction interfaces for Push, Email, AI, etc.
- **Security Layer** — Route guards + Firestore rules + Audit logging

Every admin action flows through **four predictable steps**:

```
Admin UI Action → TanStack Mutation → Provider Adapter → Firestore Write
                                                  ↓
                                        Audit Log Entry (parallel)
```

## 3. Data Flow Diagrams

### 3.1 — Admin Sends a Custom Notification

```
┌─────────────────┐
│ Admin Composes  │
│   in UI         │
└────────┬────────┘
         │ useAdminMessaging().sendNotification()
         ▼
┌─────────────────────────────┐
│ 1. Write to systemNotifications/   │
│ 2. Write to adminAuditLog/         │
└────────┬────────────────────┘
         │ Firestore trigger
         ▼
┌─────────────────────────────┐
│ Trusted Backend Worker:     │
│ fanOutNotifications         │
│ - Reads target filter       │
│ - Queries users             │
│ - Writes to users/{uid}/notifications  │
│ - Calls active PushProvider │
└────────┬────────────────────┘
         │
         ▼
┌─────────────────────────────┐
│ Active Push Provider        │
│ (FCM or WebPush)            │
│ - Fetches subscriptions     │
│ - Dispatches to browsers    │
└─────────────────────────────┘
```

### 3.2 — Push Provider Switch (Admin)

```
Admin opens Settings → Push → changes Provider from FCM to WebPush
  ↓
useAdminConfig().updatePushProvider('webpush')
  ↓
Writes to adminConfig/main.integrations.push.provider = 'webpush'
  ↓
Client-side listener detects change
  ↓
- Re-initializes Firebase Messaging (unsubscribes FCM)
- Registers WebPush VAPID subscription
- Saves new subscription to users/{uid}/private/data.pushSubscriptions.webpush
  ↓
All new notifications route through WebPushAdapter
```

### 3.3 — Admin Bans a User

```
Admin → Users Tab → Action Dropdown → Ban User
  ↓
Opens BanUserModal (reason input)
  ↓
useAdminUsers().banUser(uid, reason)
  ↓
writeBatch:
  - users/{uid}.banned = true
  - users/{uid}.bannedReason = reason
  - users/{uid}.bannedAt = serverTimestamp
  - adminAuditLog/new: { action: 'ban_user', targetUid, reason }
  ↓
Firestore rules: only isAdmin() can write these fields
  ↓
Toast success → Table refreshes → User shows Banned badge
```

  /** Server-side: send to specific users or all users */

  test(): Promise<{ ok: boolean; message: string }>;

### 4.4 Provider Factory Pattern

```typescript
// src/features/admin/providers/push/PushProviderFactory.ts

import { FCMAdapter } from './FCMAdapter';
import { WebPushAdapter } from './WebPushAdapter';
import { getAdminConfig } from '@/features/admin/hooks/useAdminConfig';

let cachedProvider: PushProvider | null = null;

export async function getPushProvider(): Promise<PushProvider> {
  const config = await getAdminConfig();
  const activeName = config.integrations.push.provider;

  if (cachedProvider?.name === activeName && cachedProvider.enabled) {
    return cachedProvider;
  }

  switch (activeName) {
    case 'fcm':
      cachedProvider = new FCMAdapter(config.integrations.push.fcm);
      break;
    case 'webpush':
      cachedProvider = new WebPushAdapter(config.integrations.push.webpush);
      break;
    default:
      throw new Error(`Unknown push provider: ${activeName}`);
  }

  return cachedProvider;
}
```

## 7. Backend Requirements and Runtime Choice

Privileged operations MUST execute on a trusted server using Firebase Admin SDK. They must never be implemented as privileged browser-side Firestore writes. **v1 primary runtime: the existing cPanel host, provided it supports a persistent Node.js application (Node.js Selector or equivalent), HTTPS, outbound requests, and cron.** cPanel hosting is not inherently free; confirm these capabilities and any provider limits before implementation. If unavailable, use Cloud Functions on Blaze or another trusted server. Firebase Spark does not provide deployable Cloud Functions.

### 7.1 cPanel Node.js Backend (v1 Primary)

Base URL: `https://api.softrly.com/admin/*`

- Verify Firebase Authentication ID tokens server-side with Firebase Admin SDK on every user-facing admin request.
- Resolve the caller's user record and require `role === 'admin'` server-side. Never trust a client-supplied role, email, UID, or admin flag.
- Keep service-account credentials, email credentials, VAPID private keys, and provider secrets in server environment variables or server-only secret storage. Do not expose them in `VITE_*` variables or client-readable `adminConfig`.
- Protect cron-only endpoints with a long random secret stored server-side and sent in an authorization header. Do not rely on an unguessable URL or unauthenticated `curl`.
- Apply request validation, rate limits, bounded batches, timeouts, idempotency, structured logs, and audit records. Return sanitized errors; never log tokens or secrets.
- Suggested endpoints:
  - `POST /admin/send-push`
  - `POST /admin/send-email`
  - `POST /admin/test-email`
  - `POST /admin/fan-out-notifications`
  - `POST /admin/recalculate-stats`
  - `POST /admin/export-data`
  - `POST /admin/process-scheduled` (cron-only)
- Browser requests include `Authorization: Bearer <Firebase ID token>`. The server verifies token and admin role before dispatch.
- cPanel cron, every five minutes: prefer a protected shell script that reads `CRON_SECRET` from a server-only file (permissions restricted to the service account), then sends it in the `X-Cron-Secret` header. Example crontab: `*/5 * * * * /home/softrly/cron/process-scheduled.sh`. Example script:
  ```bash
  #!/bin/bash
  set -a
  source /home/softrly/.env.cron
  set +a
  curl --fail --silent --show-error -X POST \
    -H "X-Cron-Secret: $CRON_SECRET" \
    https://api.softrly.com/admin/process-scheduled
  ```
  Keep `.env.cron` outside the web root with restrictive permissions; never commit or expose it.

### 7.2 Scheduled Notification Processing

Query due records where `sentAt == null` and `scheduledAt <= now()`, claim each record transactionally (for example, set a processing status/lease and unique job key), then fan out. Mark sent only after successful processing; record partial failures and retry safely. The schema therefore includes `status` (`scheduled | processing | sent | failed`) and `lastError` (sanitized, optional). Use idempotent per-user notification IDs so retries do not duplicate inbox items. A cron run must be safe to overlap.

### 7.3 Optional Cloud Functions Alternative

If the project moves to Firebase Blaze, the same server-side handlers may be deployed as Cloud Functions/Cloud Scheduler. Keep the provider/service interface independent of runtime. Do not implement both runtimes for v1.

| Function | Purpose | Trigger |
|---|---|---|
| `sendPushNotification` | Dispatch push to all matching users | HTTPS callable (admin only) |
| `sendEmail` | Send email via Resend/SMTP | HTTPS callable (admin only) |
| `fanOutNotifications` | Distribute to user subcollections | Firestore onCreate on `systemNotifications` |
| `recalculateUserStats` | Recompute all users' book counts | HTTPS callable (admin only) |
| `exportPlatformData` | Export all collections to JSON | HTTPS callable (admin only) |
| `sendScheduledNotifications` | Send scheduled notifications at their time | Cloud Scheduler (cron) |

**Runtime decision:** cPanel Node.js backend is the v1 primary, subject to hosting capability checks (Section 7.1). Cloud Functions on Blaze are the documented alternative. Do not use browser-side admin writes as a fallback.

## 8. Environment Variables and First-Admin Bootstrap

New variables needed in `.env.local`:

```bash
# Existing
VITE_FIREBASE_API_KEY=...
VITE_FIREBASE_AUTH_DOMAIN=...
# ... etc

# New — Admin Panel
VITE_FCM_VAPID_KEY=...
# No admin bootstrap secret or privileged credential belongs in VITE_*

# Server-side only (Cloud Functions or cPanel backend)
RESEND_API_KEY=...
FCM_SERVER_KEY=...
VAPID_PUBLIC_KEY=...
VAPID_PRIVATE_KEY=...
```

**First-admin bootstrap (required before opening /admin):** Do NOT promote an admin from `AuthContext.tsx` using `VITE_ADMIN_EMAIL`. Vite variables are public, and client-side promotion conflicts with the rule that only an existing admin can change roles. Bootstrap once through Firebase Console by setting `users/{uid}.role = 'admin'` for the verified owner account, or run a one-time trusted local/server script using Firebase Admin SDK. The script must take the exact UID (not just an email), verify the intended account, set the role, and then be removed/disabled. After bootstrap, normal role changes go through the authenticated admin backend and audit log.

**Security Rule:** Never commit `.env.local`, service-account files, cron secrets, or any secret file to Git. Add them to `.gitignore`. Never put server secrets in `VITE_*` variables or client-readable Firestore documents.

## 9. Security Checklist

Before deploying the Admin Panel, verify ALL of these:

- [ ] `AdminRoute` redirects non-admins to `/library`
- [ ] Firestore rules enforce `isAdmin()` for client-accessible admin data; privileged writes and secrets are server-only
- [ ] `role`, `plan`, and `banned` fields on `users/{uid}` cannot be changed by ordinary clients
- [ ] `banned` field is admin-only
- [ ] `adminAuditLog` is immutable (no update/delete); trusted server writes audit records for privileged actions
- [ ] No API keys are exposed in client-side code
- [ ] FCM/WebPush private/server keys are stored server-side (cPanel backend or Cloud Functions)
- [ ] Resend/SMTP API keys and all provider secrets are server-only; never readable by browser clients, even admins
- [ ] The admin panel route is hidden from all non-admin users
- [ ] All destructive actions have 2-step confirmation
- [ ] First admin is bootstrapped out-of-band; no client-side privilege escalation
- [ ] Cron endpoint requires a secret header; admin endpoints verify Firebase ID token and role
- [ ] Scheduled processing is transactional/idempotent and safe under retries/overlapping cron runs

## 10. Testing Strategy

### 10.0 Cross-cutting acceptance checks
- Bootstrap a first admin without enabling any client-side role escalation.
- Verify ordinary authenticated users cannot call any `/admin/*` endpoint, even if they forge request fields.
- Verify secrets never appear in browser bundles, Firestore client-readable documents, logs, or error responses.
- Run two overlapping scheduler requests and confirm no duplicate user inbox records or double sends.
- Verify seedDefaults is safe on repeated and concurrent admin loads and does not overwrite customized data.
- Verify plans are publicly readable but writable only through the trusted admin path; `adminConfig/main` is admin-only, `adminConfig/public` contains only public landing content, and secrets remain server-only.
- Verify a notification's delivery count is not presented as a read/open count.

## 11. Phase 6.1 — What to Build First

For the very first prompt to the AI agent, build ONLY this scope:

**Deliverables:**
1. `src/components/AdminRoute.tsx`
2. `src/pages/AdminPage.tsx` with tab layout
3. `src/features/admin/components/AdminTabs.tsx`
4. `src/features/admin/components/dashboard/DashboardTab.tsx`
5. `src/features/admin/components/dashboard/DashboardCharts.tsx`
6. `src/features/admin/components/dashboard/RecentActivityFeed.tsx`
7. `src/features/admin/hooks/useIsAdmin.ts`
8. `src/features/admin/hooks/useAdminStats.ts`
9. Sidebar entry in `DesktopSidebar.tsx`; in `MobileBottomNav.tsx`, replace the Insights slot with Admin for authorized admins only. Keep Insights accessible to mobile admins from the profile menu; restore Insights in the same slot for non-admins. Preserve the four-slot layout.
10. Route registration in `App.tsx`
11. `src/features/admin/hooks/queryKeys.ts` (canonical `adminKeys` definitions used by all admin queries).
12. Firestore rules update for admin-only `adminConfig/main`, public-read/admin-write `adminConfig/public`, public read-only pricing rules, and server-only privileged writes.
13. `src/features/admin/utils/seedDefaults.ts` and invocation after admin authorization on AdminPage mount. Idempotently create missing `adminConfig/main`, `adminConfig/public`, `platformPlans/free`, and `platformPlans/pro` using documented defaults; never overwrite existing admin-edited values; handle concurrent first loads. **Phase 6.1 note:** `seedDefaults` runs client-side and relies on admin-only Firestore rules to authorize writes. When the trusted backend is introduced in Phase 6.3, migration to server-side seeding is recommended but not required.

**Audit helper note:** `adminAudit.ts` is in the architecture folder structure, but implementation is deferred to Phase 6.2 when the first destructive/admin-mutating actions are built.

**Do NOT build yet:**
- Users tab
- Moderation tab
- Messaging tab
- Plans tab
- Settings tab
- Provider abstraction layers
- Cloud Functions

Those come in Phase 6.2, 6.3, etc.

**Why?** Because if we try to build all 6 tabs at once, the AI will make mistakes. We build one tab, test it, then move on.
