# Workflow

- Works from a written PRD/spec and expects the agent to read it and adhere to its scope before writing code. Confidence: 0.75
- Splits large migrations/builds into explicit phases and delivers incrementally — wants only the current phase built and later logic left out ("do not build X yet"). Confidence: 0.85
- Writes structured task briefs with Context / Goal / Tasks sections and explicit file-level deliverables. Confidence: 0.6
- Wants legacy bugs from the prior implementation carried forward and fixed during a migration (rather than silently dropped). Confidence: 0.55
- Keeps task instructions as documents inside the repo — either one numbered file per phase (e.g. `docs/p2.txt`, `docs/p3.txt`, `docs/p4.5.txt`, `docs/5.txt`, `docs/6.4.txt`, including sub-phases) or a single multi-part brief (e.g. `docs/prompt.txt` with several parts) — and points the agent at them with an `@`-mention ("read @docs\6.4.txt and execute the tasks as mentioned") to read and execute, rather than inlining the request. Confidence: 0.9
- When handed a multi-part task list, expects the agent to work the tasks sequentially one-by-one (part 1, then part 2, …), completing and verifying each before starting the next rather than batching them. Confidence: 0.6
- Expects work to be verified with the project's lint and build (type-check) scripts and the results reported before a phase is declared complete. Confidence: 0.55
- Prefers backend/infra config (Firestore rules and indexes, `firebase.json`) delivered as files to apply manually via the console, and explicitly asks that deploy/CLI commands (e.g. `firebase-tools`) not be run. Confidence: 0.5
- Expects the agent to pause for explicit sign-off on high blast-radius decisions (e.g. Firestore security rules and data-visibility model changes) before implementing, presenting the options with a recommended default rather than deciding unilaterally. Confidence: 0.5
- Wants code/commands prescribed in a task brief (e.g. an exact `package.json` script line) reproduced verbatim, and prefers the agent report environment-level failures instead of silently rewriting the prescribed text; ask before adjusting infra config. Confidence: 0.5
- Requires destructive/irreversible data operations to be gated behind a multi-step confirmation flow (e.g. a 2-step review-then-confirm modal in a "Danger Zone") with explicit "cannot be undone / back up first" warning copy. Confidence: 0.5
- When a task brief is ambiguous or internally contradictory, prefers the conservative, least-invasive resolution: chooses the minimal scope offered (e.g. "Level 1") and preserves existing working functionality rather than mechanically following delete/cleanup lists that would break it. Confidence: 0.5
- Also uses the repo prompt-file workflow to run audit-only or design-review tasks: the brief either asks for inspection of a feature/phase and an honest report of code gaps, bugs and a completeness verdict, or poses a set of explicit design questions to be answered one-by-one with a recommended decision — in both cases with no file modifications, and the agent is expected to respect that no-edit scope, not "fix" anything, and stop before writing code. Confidence: 0.5
- Values blunt, self-critical reporting (explicit gap/bug lists, "not complete", flagged intentional leftovers) over optimistic summaries; wants claims about what works grounded in the actual code read. Confidence: 0.5
- When asking to remove a feature/concept, expects it purged completely across the whole surface (dashboard cards, filters, table columns, row/action menus, types, data-layer hooks, and related tabs) rather than just the one spot named — phrases requests as "remove X, Y, or any other options". Confidence: 0.55
- When a brief mixes bug fixes with new features, expects the fixes implemented and verified first and then an explicit pause to ask for confirmation before starting the features ("fix the bugs at first and then ask for confirmation to start implementing the features mentioned; once i approve-start implementing"). Confidence: 0.65
- Explicitly requires that pre-existing features/rules/functions keep working ("don't break other features/rules/functions", "don't break any existing features", "DON'T BREAKE ANY EXISTING FEATURES") — changes must be scoped so existing behavior (e.g. desktop) is preserved while the new/buggy path is altered. Confidence: 0.7
- When specifying that some data should be hidden/excluded (e.g. books marked "not in library"), expects the rule enforced consistently across every surface that lists or aggregates that data — item lists, profile/header totals, and insights stats — so displayed counts always match the filtered/visible set, not just the single surface where the issue was first noticed. Confidence: 0.5
- After a fix/implementation pass, expects a complete written report of the changes made ("fix the issues mentioned and at the end provide a complete report of changes you made") — mapping work back to the requested items and listing the files touched. Confidence: 0.55
- Reuses an agent-produced report/audit saved in the repo (e.g. `docs\Audit.txt`) as the input for the next task, asking the agent to fix every issue it previously reported. Confidence: 0.5
- Treats the diagnosis/prescribed fix inside a brief as a hypothesis, not gospel: "fix the issue mentioned properly" means verify the claim against the real code, fix the actual root cause, and explicitly report where the brief's premise was wrong (even if none of the suggested fixes apply). Confidence: 0.5
- Expects new UI flows/actions to be reachable from every entry point that surfaces the triggering interaction, not just the one page named in the brief — a shared component used across pages (e.g. a book-details modal) should own the flow so it fires everywhere, and states that may already exist (e.g. an already-finished book) still need a manual path to the action. Confidence: 0.55
- Prefers in-app confirmation modals (custom UI with the app's own components and warning copy) over the native browser `window.confirm` for destructive actions like deleting a book. Confidence: 0.55
- For destructive/account-deletion operations, requires the wipe to be scoped strictly to the acting user's own data and to explicitly protect shared/other-user data — never delete collaborators' books/data, and leave shared or immutable records intact. Confidence: 0.55
- Reports runtime bugs by pasting the verbatim browser error/stack trace (e.g. "Uncaught Error: Maximum update depth exceeded… at ReadingPlan.tsx:68") and expects the agent to diagnose and fix the actual root cause (e.g. unstable reference / unguarded setState loop), not just mask the symptom, then re-run typecheck/lint/build. Confidence: 0.55
- Describes a failing bug partly by its conditions/scale ("maybe when the amount of books is huge") and expects the agent to reason about the underlying cause (e.g. a whole-export rejecting when any one image fails) rather than treating the reported error string itself as the root cause. Confidence: 0.5
- Wants public-facing/marketing content (landing, about page, etc.) to be admin-editable — authored through the existing admin public-config document with shipped defaults and an admin editor — rather than hardcoded in components. Confidence: 0.5
- Comfortable delegating copy/content authoring to the agent when asked ("provide some project info ... by yourself"), expecting sensible self-written default copy (e.g. feature list, how-it-works, technical info) without needing it supplied. Confidence: 0.5
- For cross-user interactions, expects the other user's privacy/permission settings to be honored — the action is only surfaced in the UI when their setting allows it, with the permission still enforced server-side rather than bypassable from the client. Confidence: 0.5
